# Дашборд Service Desk — заявки / проблемы / графики / отчёт F-4

Локальное веб-приложение поверх `connectors/servicedesk/client.py` (та же
cookie-сессия, что у остальных скриптов синка). Вкладки в браузере:

1. **Заявки** — все заявки за период (свой диапазон дат или пресеты
   сегодня/7д/30д), фильтры по комплексу/влиянию/статусу/узлу/инженеру,
   сортировка по клику на заголовок любой колонки. Заявки с длительностью
   работ ≥ порога (настраивается, по умолчанию 4 ч) подсвечены красным.
   Заявки, у которых "время начала работ" РАНЬШЕ времени регистрации
   инцидента (физически невозможный порядок — сигнал ошибки в датах),
   подсвечены отдельно (жёлтая полоса слева + бейдж с величиной сдвига в
   часах); пилюля "Только требующие проверки" фильтрует оба типа аномалий
   разом, плюс заявки без привязанной проблемы (синяя полоса слева +
   «нет проблемы»). Клик по строке —    карточка заявки: редактирование любых полей
   (заголовок, вид работ, влияние, приоритет, статус, узел, инженер, привязанная
   проблема, времена инцидента/начала работ/закрытия, описание/действия L1/
   диагностика/причина отказа/работы/материалы/результат/акт/флаги акта/
   комментарий), просмотр вложенных фото/файлов
   (картинки открываются во встроенном лайтбоксе по клику — data:-ссылки
   нельзя открывать через target=_blank, браузер их блокирует; остальные
   файлы — по клику скачиваются) и загрузка новых файлов прямо из
   браузера. В карточке — кнопки "Пред./След." (и стрелки ←/→ на
   клавиатуре) для перехода по заявкам без закрытия окна, в порядке того
   списка, из которого заявку открыли (с учётом текущих фильтров и
   сортировки); при несохранённых правках переход/закрытие спросит
   подтверждение.
2. **Проблемы** — список отсортирован по активности связанных заявок (новые
   сверху по умолчанию; есть переключение на сортировку по названию/числу
   заявок/числу открытых, плюс фильтр "только с открытыми"; сама сущность
   problem не хранит дату создания в API, поэтому "новизна" = дата
   последней связанной заявки). Клик по проблеме — полный текст + таблица
   привязанных заявок (с фильтрами по влиянию/статусу и сортировкой по
   колонкам). Клик по заявке в этой таблице открывает ту же карточку
   редактирования, что и на вкладке "Заявки" — можно править данные, не
   переключаясь между вкладками. Кнопка «Объединить проблемы» — merge
   описаний + перенос `problemId` у заявок с прогрессом по каждой.
3. **Графики** — динамика простоя и времени на объекте по комплексам F-4
   (`GET /api/report/charts`). Типы: линии / stacked area / сглаженный stack /
   **Недели** / столбцы / простой vs на объекте. Тип «Недели»
   (`GET /api/report/weekly`): ISO-недели, Y флота = обрезанный по графику
   работы простой / N действующих комплексов (активны с даты первой заявки);
   монтаж/ПНР по ключевым словам исключён; ряды по комплексам; клик по
   столбцу — заявки недели. Остальное: именованные виды в localStorage,
   зум колесом, тренд, исключённые заявки, карточка по клику.
4. **Монтаж/ПНР** — заявки, прошедшие фильтр даунтайма отчёта F-4, но
   отнесённые к монтажу/ПНР по тексту (`title`/`description`/`workDone`/
   `diagnosis`: монтаж, демонтаж, пнр, пусконалад…). В недельный график
   не входят; клик по строке — та же карточка заявки.
5. **Отчёт F-4** — даунтайм-аналитика флота F-4 по методике из
   `backend/analysis.py` (докстринг там же подробно объясняет все решения):
   теплокарта день×комплекс со слоями (весь даунтайм/молочка/софт/
   механика/прочее/удалённо/обновление ПО), список заявок по клику на
   день/ячейку, кликабельная сводка по комплексам, bar chart флота,
   финальный текстовый отчёт по периоду.

## Запуск

Проще всего — двойной клик по `start_dashboard.bat` в этой папке. Он
поднимет сервер на `http://localhost:8765` через venv `connectors/servicedesk/venv`
(там уже стоят fastapi/uvicorn/curl_cffi после установки 2026-08-12).
Открой `http://localhost:8765` в браузере — фронтенд отдаётся тем же
сервером (без сборки, React+htm через esm.sh CDN).

Вручную:
```
cd servicedesk_dashboard\backend
..\..\connectors\servicedesk\venv\Scripts\python.exe app.py
```

Если venv когда-нибудь пересоздаётся с нуля — доустановить зависимости:
```
python.exe -m pip install -r requirements.txt
```
(в этом venv `pip.exe` сам по себе битый — см. память проекта, всегда
`python.exe -m pip ...`).

## Данные / кэш

Бэкенд держит в памяти кэш `get_tickets()`/`get_problems()` на 120 секунд
(эти вызовы у Service Desk небыстрые — тянут вложения). Кнопка "Обновить
данные" в шапке дёргает `/api/refresh` принудительно. После любого
редактирования заявки кэш обновляется автоматически.

## Методика отчёта F-4 — важные решения (кратко, подробности в analysis.py)

- **День на теплокарте = `workStartedAt`** ("время начала работ"), не
  incidentAt/createdAt. Без этого поля заявка не попадает в календарь,
  считается отдельно (счётчик "без даты работ").
- **Длительность = `workStartedAt` → `closedAt`** (это и есть "время на
  объекте до времени окончания инцидента" по вашему определению). Если
  `workStartedAt` позже `closedAt` (встречается в реальных данных — самый
  известный пример SD-1166) — длительность НЕ считается, заявка попадает в
  отдельный счётчик "Некорр. время" вместо того, чтобы тянуть мусорное
  отрицательное число в отчёт.
- **Merge пересекающихся интервалов — отдельно по каждой паре
  (комплекс, kind)**, не глобально. Это гарантирует, что общий % ровно
  равен сумме % по видам (молочка+софт+механика+прочее) — если бы мёржили
  всё подряд, сумма долей могла бы разъехаться с общим при пересечении
  заявок разных видов.
- **kind** определяется по полю `ticket.node` (чистый категориальный
  справочник Service Desk), а не текстовым поиском — надёжнее.
- **Удалённо** = нет признаков выезда (акт/фото акта/номер акта/текстовые
  маркеры "на объекте"/"по приезде"/"выезд"…) И это не обновление ПО с
  явным приездом/актом/длительностью ≥ 1ч.
- **Отдельная проверка (не влияет на часы простоя, только подсветка для
  ручного контроля): `workStartedAt` РАНЬШЕ `incidentAt`.** Это другая пара
  времён, чем длительность выше (там workStartedAt vs closedAt) — здесь
  проверяется, что "время на объекте" не может начаться раньше, чем
  зарегистрирован сам инцидент. Живой пример — SD-1213: инцидент
  08.08 16:00, а начало работ проставлено 08.08 10:49 (на 5ч17м раньше).
  Такие заявки помечены жёлтым во вкладке "Заявки" и попадают в счётчик
  "Начало раньше инцидента" в отчёте — стоит поправить дату/время в самой
  заявке через карточку редактирования.

## Известная особенность живых данных (2026-08-12)

На срезе 13.07–11.08 у **91 из 214** заявок F-4 `workStartedAt` оказался
ПОЗЖЕ `closedAt` (не только у известного примера SD-1166). У большинства
разница — секунды/минуты (похоже на то, что оба поля проставляются почти
одновременно при закрытии заявки, `workStartedAt` — авто-таймштамп клика,
`closedAt` — вручную введённое округлённое время), но у части разница в
часы и даже дни (SD-1164 — почти 30 дней) — это уже похоже на реальную
ошибку заполнения. Все такие заявки исключены из часов простоя (не
занижают историю искусственно) и явно перечислены в отчёте отдельным
блоком "Некорректное время" — стоит время от времени проходиться по этому
списку и поправлять `workStartedAt` через вкладку "Заявки".
